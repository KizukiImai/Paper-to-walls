# v1.1 — 別PCへの送信と手描き線の直線化

## 最初に：2台の役割

```text
操作側PC A                                Unity側PC B
start.bat（通常3000）                     start-receiver.bat（通常3001）
  ↑ ブラウザ・スマートフォン                ↓ 受信JSONを保存
  └─ Web UIでBのIPとポートを指定 ──POST──→ 受信サーバー
                                           ↓ localhostから取得
                                         Unityで壁を生成
```

IPとポートだけでは、Unityが自動的にHTTPを受信するわけではありません。**PC Bには受信サーバーが必要です。** 今回はNode.js受信サーバーを同梱し、WindowsのHTTP待受け権限設定をUnityのC#コードに持たせない方式です。ブラウザから相手へ直接クロスオリジンfetchするのではなく、PC AのサーバーからPC Bへ中継します。

### 1. 操作側PC A

新しいZIPを展開して `start.bat` を起動し、表示されたアドレスでWebアプリを開きます。標準は `http://localhost:3000` です。スマートフォンはPC AのLANアドレスを使ってください。

### 2. Unity側PC B

同じZIPをPC Bにもコピー・展開します。Node.jsを利用できる状態にして、**`start-receiver.bat`** を起動します。聞かれたポートに `3001` を入力するか、そのままEnterを押します。起動した黒いウィンドウは閉じずに残します。

起動ログの `LAN:` に、例えば次が表示されます。

```text
http://192.168.1.50:3001
```

ここにある `192.168.1.50` が送信先IP、`3001` が送信先ポートです。複数のLANアドレスが表示される場合は、PC Aと通信できるWi-Fi/Ethernet側を選びます。VPNや仮想ネットワークのアドレスでは接続できない場合があります。

必要に応じ、PC BのWindows Firewallで、Node.jsまたは指定TCPポートを**利用するプライベートネットワーク内だけ**許可します。ファイアウォール全体を無効化しないでください。アプリはFirewall設定を自動変更しません。

### 3. Web UIの送信設定

右のEXPORT欄で次を指定します。

| 項目 | 例 |
|---|---|
| 送信先 | 別PCのUnity受信サーバー |
| 受信PCのIPv4 | `192.168.1.50` |
| ポート | `3001` |

「接続テスト」で受信サーバーの稼働を確認した後、「指定PCへJSONを送信」を押します。**同一ネットワークでも端末分離などがあると通信できません。**

送信先のIP・ポート・モードは、ブラウザが保存を許可している場合にlocalStorageへ記憶します。受信キーは記憶しません。キーを除き、次回も同じ送信先を使えます。HTTPのみ、IPv4の `10.*` / `172.16〜31.*` / `192.168.*` および検証用ループバックに対応します。ホスト名・IPv6・公開IPへの送信は対象外です。

**「受信PCに保存済み」はUnityで表示されたという意味ではありません。** Unityの実行・描画結果は送信側で確認していません。送信失敗後に再送するとrevisionが増えます。通信切断のタイミングによっては先の送信が保存済みの可能性があるため、最新JSONを確認できます。

### 4. Unity側の取得先

PC B上のUnityは、同じPC Bの受信サーバーから取得します。

```text
http://127.0.0.1:3001/api/layouts/latest
```

既にある `LayoutReceiver` の取得先を上記に変更します。ポートを変更した場合は、ここも合わせます。Web側へ入力するIPは**PC BのLANアドレス**であり、`127.0.0.1` ではありません。後者はUnityから同じPC Bへ接続するときだけ使用します。

既存の受信・壁生成コードがない場合は、`unity-bridge/PaperSpaceLayoutReceiver.cs` を `Assets/Scripts` にコピーし、空のGameObjectにアタッチしてPlayします。`serverBaseUrl` の初期値は `http://127.0.0.1:3001` です。既存の生成コードと同時に動かすと壁が重なるので、どちらか一方を使ってください。

このサンプルはJSON取得・検証・Cube生成・全置換までを行う最小構成です。カメラやシーン自体は作成しません。URP/HDRPなどを使う場合は、対応する壁マテリアルを `wallMaterial` に設定してください。Unityの描画動作およびC#コンパイルは今回の環境では実行していません。

Unityで「Insecure connection not allowed」などが出る場合は、`Edit > Project Settings > Player > Other Settings > Configuration > Allow downloads over HTTP` を確認してください。この信頼できるLAN内のHTTP構成で、実行するEditor/ビルドに合う許可設定が必要です。アプリはこのセキュリティ設定を自動変更しません。外部配信用のプロジェクトへ変更を無条件に流用しないでください。

### コマンドで受信側を起動する場合

```powershell
$env:PORT = "3001"
$env:HOST = "0.0.0.0"
$env:RECEIVE_ONLY = "1"
$env:DATA_DIR = "$PWD\receiver-data"
node server/index.mjs
```

`start-receiver.bat` はこの受信専用設定を行います。受信専用では、さらに別のPCへ転送するAPIは無効です。PC Bの `receiver-data/latest-layout.json` に最新データが残り、再起動後も復元されます。送信側の `user-data` にはリモート送信データを勝手に保存しません。

### 任意の受信キー

受信PCで `RECEIVE_KEY` 環境変数を指定して起動すると、保存POSTにキーを要求できます。Web UIの「受信キー」に同じ値を入れます。キーは半角の印字可能文字で256文字以下、空白は不可です。

```powershell
$env:RECEIVE_KEY = "your-random-shared-key"
.\start-receiver.bat
```

キーは保存する壁JSONに入りません。接続テストはサーバー稼働を確認するだけで、キーの正誤は実際の送信時に検証します。HTTPなので暗号化されず、公開サービス用の認証ではありません。信頼できるLAN内だけで利用し、インターネットへのポート開放はしないでください。

## 手描き線の直線化

左側に「手描きの揺れを、直線に。」を追加しています。

1. 写真を取り込み、四隅を指定して認識します。
2. **「直線化の強さ」0〜100**を変更します。標準は40です。
3. **「補正を反映する」**を押します。写真に重ねて結果を確認します。
4. 強すぎる場合は弱めて再適用、またはUndoで戻します。

0も画素ノイズの整理を行う最小補正で、ピクセルを一切変えない設定ではありません。「弱15」「標準40」「強80」のプリセットもあります。スライダーの変更だけでは出力JSONは変わりません。反映ボタンまたは画像の再認識で確定します。

### 水平・垂直への補正とは別です

「直線化」は**斜め線にも対応**し、揺れた線を一本の近似直線へまとめます。「ほぼ水平・垂直の線を補正」は、近似線の方向が軸に近い場合だけ水平・垂直へ寄せます。角度は0〜12°で別に調整でき、初期値は3°です。斜めの壁をそのまま残したい場合はチェックを外してください。

「つなぐ隙間」「交点の補正距離」は従来どおり別設定です。直線化を強めたことだけを理由に、離れた別のストロークをまとめる閾値は拡大しません。ただし、強い近似で形が変わり新たな交差が生じたり、ごく小さい隙間が既存の交点スナップに吸収されたりする可能性はあります。小さな角・短い壁の消失を含め、写真との比較が必要です。

### 計算と編集の扱い

- 二値化・細線化の結果から追跡した**元の中心線**を保持します。補正後の線に補正を繰り返し加える方式ではありません。
- RDPで折れ線を区切り、各区間の全点を使う直交最小二乗法で直線を推定します。共有する元端点は同じ接続点として解き、T字などの接続を維持するようにします。
- 強さによる許容幅は処理解像度に比例します。補正だけの再計算では画像の二値化・細線化はやり直しません。
- 再補正時は現在の縮尺・壁の高さ・厚さを保持します。
- 手動編集がある場合は、置換前に確認します。置換後もUndoで戻せます。
- Undo/Redoは線の履歴です。スライダーの値は「次に適用する設定」として残り、履歴操作後にその旨を表示します。
- 作業ファイルには補正設定と元の中心線も保存します。v1.0の作業ファイルは開けますが、補正用の元線が含まれないため写真から再認識が必要です。壁JSONだけでは元の手描きの形は復元できません。

左のサンプル選択で「波打った1本線」「揺れのある手描き風間取り」を試せます。これらは合成画像です。自動テストでは80の設定で、前者が1線分、後者がT字分割を含む8線分になっています。実写で同じ精度を保証するものではありません。

## API互換性

Unity用のJSONは変更しません。`schemaVersion:1`、`layoutId`、`revision`、`units:"m"`、`wallHeight`、`wallThickness`、`walls[{id,ax,ay,bx,by}]` を維持します。

新しいAPIは**操作側サーバー向け**の中継APIです。

```text
POST /api/targets/check
{ "target": { "host": "192.168.1.50", "port": 3001 } }

POST /api/targets/send
{ "target": { "host": "192.168.1.50", "port": 3001 }, "layout": <壁JSON> }
```

相手PCへは従来と同じ `POST /api/layouts` に壁JSONだけを送信し、受信サーバーがrevisionを割り当てます。`GET /api/layouts/latest` は従来どおりです。旧版の同梱サーバーも基本契約は同じですが、受信専用モード・キー機能・修正点をそろえるため、両PCともv1.1の使用を推奨します。

中継は送信先検証、固定APIパス、最大1MB、段階ごとのタイムアウト、リダイレクト拒否、JSON検証を行います。保存確認の応答が送信内容と一致しない場合は成功と表示しません。画像・作業ファイル・補正設定は相手PCに送信しません。

## 更新方法と残る確認

旧サーバーを停止し、新しいZIPを別フォルダーへ展開して起動してください。旧 `user-data` と作業ファイルはバックアップし、必要なら移行します。ブラウザを再読み込みして新UIを確認してください。

Node.jsの自動テストと検証環境の制限は `TESTING.md` に記載しています。WindowsのFirewall、実際の2台間LAN、スマートフォンの撮影、Unityの実行は利用環境での確認が必要です。
